# COLLABORATIVE ASSERTION ASSESSMENT AND USER-SUGGESTED ASSERTIONS

Assertions are versioned, collaborative propositions. They may be generated by a model, proposed by a user, created by a reviewer, or imported. Each assertion must preserve its author, origin, evidence, revision history, review status, and temporal scope.

Users may rate each assertion revision from 1 to 5 according to its perceived strength. Ratings are subjective user assessments and must remain separate from model confidence, evidentiary strength, and formal review status.

Users may suggest assertions from highlighted source text, selected provisions, graph nodes, search results, or existing assertions. User-suggested assertions begin as drafts or proposals and require review before appearing as accepted legal relationships. Authorized users must be able to:

1. Rate the perceived strength of an assertion from 1 to 5.
2. Add an optional explanation for their rating.
3. Suggest new assertions.
4. Attach exact documentary evidence to an assertion.
5. Edit or withdraw their own unreviewed assertions.
6. Review the history, evidence, ratings, and status of an assertion.

A user rating represents that individual user's opinion regarding the strength of the assertion. It is not a judicial finding, legal conclusion, model-confidence score, or substitute for formal review.

The system must keep the following concepts strictly separate:

- Model confidence
- Deterministic extraction confidence
- Formal review status
- Individual user strength rating
- Aggregate user strength rating
- Evidentiary support
- Legal validity

Do not combine these concepts into a single score.

==================================================
1. ASSERTION TYPES AND ORIGINS
==================================================

An Assertion represents a contestable proposition concerning one or more graph entities.

Examples:

- A judgment interprets a statutory provision.
- A contractual clause creates an exception to another clause.
- Two definitions materially conflict.
- An amendment modifies a specific obligation.
- A policy applies to a specific business unit.
- A provision is likely relevant to a particular legal issue.
- One authority weakens or supports another authority.
- An obligation survives termination.
- Two clauses may be legally distinguishable despite textual similarity.

Each assertion must have an origin:

- model_suggested
- user_suggested
- reviewer_created
- imported
- system_generated

A user-suggested assertion must never become an accepted assertion merely because it was submitted or highly rated.

All newly submitted user assertions begin with one of the following statuses:

- draft
- proposed

Only an authorized reviewer may change an assertion to:

- accepted
- rejected
- disputed
- superseded

High user ratings must not automatically change review status.

Model confidence ≠ user rating ≠ evidence strength ≠ review status ≠ legal correctness

==================================================

- id

- matter_id
- assertion_type
- proposition
- subject_entity_type
- subject_entity_id
- object_entity_type
- object_entity_id
- origin

- author_user_id
- confidence
- jurisdiction
- effective_from
- effective_to
- created_at
- updated_at
- submitted_at
- reviewed_by
- reviewed_at
- superseded_by_assertion_id
- current_revision_number

Rules:

- object_entity_type and object_entity_id may be null for assertions expressed as standalone propositions.
- confidence is reserved for machine or rule-based extraction confidence.
- User-created assertions should normally have confidence set to null.
- Do not derive model confidence from user ratings.
- Every assertion must be scoped to a repository and matter.
- Assertions must obey matter-level authorization rules.
- The proposition must be stored as authored and must not be silently rewritten by a language model.

Implement an AssertionEvidence join entity because an assertion may rely on multiple source spans.

AssertionEvidence:
- id
- assertion_id
- source_span_id
- evidence_role
- added_by_user_id
- created_at

Supported evidence roles:

- supports
- contradicts
- contextualizes
- qualifies
- primary_basis
- secondary_basis

An accepted assertion should normally have at least one supporting source span.

The application may allow a user to submit an assertion without documentary evidence, but it must be prominently marked:

- unsupported
- awaiting_evidence

An unsupported assertion cannot be formally accepted until a reviewer either attaches sufficient evidence or explicitly records a reason for accepting it without direct documentary support.

==================================================
4. USER STRENGTH RATINGS
==================================================

Implement a per-user assertion-strength rating system.

Each authorized user may assign one current rating to each assertion:

1 — Very weak
2 — Weak
3 — Plausible or mixed
4 — Strong
5 — Very strong

The labels must be displayed in the interface and should be configurable.

Implement:

AssertionRating:
- id
- organization_id
- repository_id
- matter_id
- assertion_id
- user_id
- strength
- rationale
- created_at
- updated_at

Database constraints:

- strength must be an integer from 1 through 5.
- A user may have only one current rating per assertion.
- Enforce a unique constraint on assertion_id and user_id.
- A rating must belong to the same repository and matter as the assertion.
- A user must have access to the matter before rating the assertion.

Behavior:

- Submitting a new rating creates the user's rating.
- Submitting another rating updates that user's existing rating.
- Updating a rating must create an audit event.
- A user may remove their rating.
- Removing a rating must create an audit event.
- A rating may include an optional rationale.
- Rating rationales must be visible only to users authorized to view the assertion.
- Ratings must not be exposed across matter boundaries.

Store rating history through AuditEvent or a dedicated AssertionRatingRevision entity.

For every assertion, calculate:

- Number of ratings
- Arithmetic mean
- Median
- Distribution across 1, 2, 3, 4, and 5
- Current user's rating
- Date of the current user's last rating
- Number of ratings containing a rationale

Do not calculate or display an aggregate when there are no ratings.

Do not round the stored calculation. The UI may display the average to one decimal place.

The aggregate rating is descriptive only. It must not:

- Automatically accept or reject the assertion
- Change model confidence
- Change evidentiary status
- Cause the assertion to be added to the accepted legal graph
- Be described as a probability that the assertion is legally correct

==================================================
7. USER-SUGGESTED ASSERTION VALIDATION
==================================================

Validate user-submitted assertions before storage.

Requirements:

- Proposition cannot be empty.
- Repository and matter must be present.
- Subject entity must belong to the same authorized matter.
- Object entity, when present, must belong to the same authorized matter or be an authorized shared external authority.
- Attached source spans must belong to documents the user is authorized to access.
- A user cannot attach evidence from another inaccessible matter.
- Dates must be logically consistent.
- Assertion type must come from an allowed controlled vocabulary or be explicitly marked as a proposed new type.
- Raw HTML and scripts must be sanitized.
- Submitted text must not be treated as system or model instructions.

The interface should warn the user when:

- No evidence is attached.
- The assertion duplicates or closely resembles an existing assertion.
- The proposed subject and object are already connected by a similar accepted assertion.
- The evidence appears to contradict the proposition.
- The assertion concerns a document version outside the selected effective date range.

Similarity warnings must not prevent submission unless there is an exact duplicate.

==================================================
8. DUPLICATE AND RELATED ASSERTION DETECTION
==================================================

Before a user submits an assertion, search for:

- Exact proposition matches
- Same subject, assertion type, and object
- Semantically similar propositions
- Superseded versions
- Accepted assertions concerning the same relationship
- Competing or contradicting assertions

Show possible matches to the user.

Allow the user to:

- Open the existing assertion
- Rate the existing assertion instead
- Add additional evidence to the existing assertion, subject to permission
- Continue submitting a distinct assertion
- Mark the new assertion as contradicting or qualifying an existing assertion

Do not automatically merge assertions.

9. ASSERTION DISCUSSION AND RATIONALES
==================================================

Allow users to explain their assessments.

A rating rationale belongs to that specific user rating.

A general assertion comment belongs to the assertion as a whole.

Implement:

AssertionComment:
- id
- assertion_id
- user_id
- parent_comment_id
- comment_text
- created_at
- updated_at
- deleted_at

Requirements:

- Comments must be matter-scoped.
- Comments must be audited.
- Users may edit or delete their own comments.
- Deleted comments should be soft-deleted where audit requirements apply.
- Reviewer comments should be visually distinguishable.
- Comments are not evidence unless explicitly converted into or linked to an AssertionEvidence record.

10. REVIEW WORKFLOW FOR USER ASSERTIONS
==================================================

The review queue must include user-suggested assertions.

Reviewers must be able to filter by:

- User-suggested assertions
- Model-suggested assertions
- Assertion type
- Author
- Date
- Rating average
- Number of ratings
- Evidence status
- Review status
- Jurisdiction
- Effective date
- Potential duplicates
- Potential conflicts

For each assertion, the reviewer must see:

- Current proposition
- Original proposition
- Revision history
- Author
- Origin
- Evidence
- Contradicting evidence
- User ratings
- Rating distribution
- Rating rationales
- Comments
- Similar assertions
- Potential conflicts
- Model confidence, where applicable

A reviewer may:

- Accept
- Reject
- Mark disputed
- Request revision
- Attach additional evidence
- Modify the assertion through a recorded revision
- Link it to a competing assertion
- Mark it as superseding another assertion
- Return it to the author with comments

Reviewer decisions must not erase prior user ratings.

When an assertion is materially revised, the interface must make clear whether existing ratings apply to:

- The old revision
- The current revision
- The assertion generally

For the MVP, associate ratings with a specific assertion revision.

When a new material revision is created:

- Preserve ratings attached to the previous revision.
- Do not automatically copy ratings to the new revision.
- Inform users that the revised assertion has not yet been rated.
- Allow users to submit a new rating for the new revision.

Implement the AssertionRating entity with:

- assertion_id
- assertion_revision_id

Enforce one current rating per user per assertion revision.

==================================================
11. GRAPH BEHAVIOR
==================================================

Accepted assertions may be projected into Neo4j as Assertion nodes.

Proposed, disputed, and rejected assertions must not appear as accepted legal relationships in the default graph view.

The graph explorer should offer an optional "Show unreviewed assertions" mode.

When enabled, display different visual states for:

- Accepted
- Proposed
- Disputed
- Rejected
- Superseded

Do not encode user rating as factual strength of a graph relationship.

The graph may display:

- Aggregate rating
- Rating count
- Review status
- Evidence count

These values must be visually and semantically distinct.

PostgreSQL remains the authoritative source for individual ratings and rating history. Any rating aggregates stored in Neo4j must be rebuildable projections.

==================================================

- Values below 1 or above 5 are rejected.
- Non-integer ratings are rejected.
- A user can update their rating.
- Updating does not create two current ratings.
- Rating history or audit history is preserved.
- A user can remove their rating.
- Aggregate mean is calculated correctly.
- Median is calculated correctly.
- Distribution is calculated correctly.
- A user without matter access cannot view or rate an assertion.
- A user cannot rate an assertion from another matter.

- A suggested assertion is not automatically accepted.
- Evidence from another matter cannot be attached.
- A user can edit their own draft.

- Proposed assertions do not appear as accepted graph edges.

19. EVALUATION AND ANALYTICS
==================================================

Track product metrics without treating them as legal-quality metrics.

Useful metrics include:

- Number of user-suggested assertions
- Percentage supported by evidence
- Percentage accepted
- Percentage rejected
- Percentage disputed
- Median time to review
- Number of ratings per assertion
- Rating distribution
- Frequency of rating changes after revision
- Agreement between reviewers and contributors
- Assertions with high rating disagreement
- Assertions with high ratings but insufficient evidence
- Assertions with strong evidence but low user ratings

Flag assertions with polarized ratings, for example where substantial numbers of users rate both 1–2 and 4–5.

Do not automatically resolve disagreement. Surface it for review.

==================================================
20. UPDATED DEFINITION OF DONE
==================================================

The collaborative assertion functionality is complete only when:

1. An authorized user can create a draft assertion.
2. The user can attach one or more exact source spans.
3. The user can submit the assertion for review.
4. The assertion is visibly marked as user-suggested.
5. Another authorized user can rate the assertion from 1 to 5.
6. The user can provide an optional rationale.
7. The user can update or remove their rating.
8. The interface displays the average, median, count, and distribution.
9. The interface separately displays model confidence, review status, and evidence status.
10. A reviewer can inspect the proposition, evidence, ratings, and comments.
11. A reviewer can accept, reject, dispute, or request revision.
12. A material edit creates a new assertion revision.
13. Ratings remain associated with the revision that was rated.
14. Proposed assertions do not appear as accepted facts in the default graph.
15. All assertion and rating actions are permission-checked and audited.
16. Automated tests confirm that assertion data and rating aggregates cannot cross matter boundaries.
